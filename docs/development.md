# طريقة العمل والإصدارات

## الحفظ والتتبع

حفظ الملف محلي. `git commit` يسجل التغييرات محلياً، و`git push` يرفع commits إلى GitHub. لا يوجد رفع تلقائي عند حفظ الملفات.

نراجع `git diff` والملفات المحددة قبل كل commit، ونرفع التقدم عند اكتمال جزء منطقي أو نهاية جلسة العمل. لا نضع ملفات الأسرار أو بيانات المستخدم في سجل Git.

## الفروع

- `main`: الكود المقبول بعد المراجعة والفحوصات المتاحة.
- `feat/<name>`: ميزة محددة.
- `fix/<name>`: إصلاح محدد.
- `docs/<name>`: تحديث التوثيق.

كل تغيير بعد التأسيس يصل إلى main عبر Pull Request. نفضل Squash merge للحفاظ على سجل واضح، ولا نحتاج فرع develop حالياً.

```sh
git switch main
git pull --ff-only
git switch -c feat/document-editor
# Edit and verify the change, then stage specific files.
git add src/path/to/changed-file.ts
git diff --cached
git commit -m "feat: add document editor"
git push -u origin feat/document-editor
```

المسار أعلاه مثال يُستبدل بالملف الفعلي بعد تأسيس التطبيق.

## إعداد GitHub بعد الربط

- حماية main من الحذف والدفع القسري واشتراط Pull Request.
- اشتراط فحوصات CI بعد إضافتها وتشغيلها لأول مرة؛ لا نفرض أسماء فحوصات غير موجودة.
- لا نشترط موافقة مساهم آخر عندما يكون المالك هو المساهم الوحيد.
- تفعيل تنبيهات الاعتماديات وفحص الأسرار وPush protection والإبلاغ الخاص عن الثغرات حيث تتاح.
- منح GitHub Actions صلاحيات القراءة افتراضياً، وصلاحية الكتابة لوظيفة النشر فقط عند الحاجة.

تم تطبيق حماية main مع اشتراط Pull Request دون اشتراط موافقة شخص آخر، ومنع الدفع القسري والحذف. تم تفعيل تنبيهات الاعتماديات وفحص الأسرار ومنع رفعها والإبلاغ الخاص عن الثغرات، وضبط صلاحيات Actions الافتراضية للقراءة. تضاف الفحوصات الإلزامية عند تأسيس التطبيق.

## الإصدارات

نبدأ بـ `0.1.0-alpha.1` عند توفر نسخة تجريبية، ثم `0.1.0`. نستخدم إصدارات `0.x` خلال التطوير الأولي ونوثق أي تغييرات غير متوافقة. بعد `1.0.0` نرفع الرقم الرئيسي للتغييرات غير المتوافقة، والفرعي للميزات المتوافقة، ورقم التصحيح للإصلاحات المتوافقة.

عند الإصدار:

1. حدّث رقم النسخة وملف lock وسجل التغييرات في Pull Request.
2. شغّل الفحوصات والبناء واختبر التثبيت والترقية واستعادة البيانات حسب التغيير.
3. بعد الدمج، أنشئ tag مثل `v0.1.0` يشير إلى commit الإصدار.
4. ابنِ ملف التثبيت من ذلك tag، وجهز GitHub Release مع الملاحظات وملفات التنزيل.
5. راجع الحزمة وانشر الإصدار؛ الإصدارات التجريبية توسم Pre-release.

لا ننشئ tags لمجرد تعديل الملفات، ولا نغيّر tag لإصدار منشور؛ نصدر رقماً جديداً عند التصحيح. ملفات التثبيت تُرفق بالإصدارات ولا تدخل تاريخ المصدر.

## قاعدة البيانات

تدخل ملفات schema وmigrations في Git، أما قواعد بيانات المستخدمين فلا. إصدار مخطط البيانات مستقل عن رقم إصدار التطبيق. قبل أي ترقية تغير البيانات، نوفر مسار نسخ احتياطي واختبارات ترقية مناسبة؛ الرجوع إلى كود أقدم لا يعيد قاعدة البيانات تلقائياً.

## الفحوصات الآلية

تضاف GitHub Actions مع تأسيس التطبيق وملف الاعتماديات: تثبيت من lockfile، فحص TypeScript، التنسيق، الاختبارات والبناء على Windows. لا توجد حالياً workflow تزعم اختبار تطبيق لم يُنشأ بعد.
